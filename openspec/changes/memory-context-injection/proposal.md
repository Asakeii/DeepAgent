# 长期记忆上下文注入

## 背景

`long-term-memory` 已经提供了 `memories` 表、显式写入和查询 API，但 Agent 运行时还不会读取长期记忆。这样用户即使明确要求“请记住我的偏好”，后续研究或打卡回合也无法稳定复用这些信息。

## 目标

- 在每次 chat run 通过 thread ownership 校验后，从共享数据库按 `user_id` 检索长期记忆。
- 将少量高优先级记忆注入 Agent 上下文，供研究工作流和打卡 Agent 个性化参考。
- 保持服务无状态：所有记忆来源于 MySQL，不依赖单 pod 进程内缓存。
- 控制上下文膨胀：限制记忆条数和单条长度。
- 避免记忆污染历史：注入的 system message 不写回 `messages` / checkin 历史。

## 非目标

- 不在本次引入向量数据库、embedding 检索或自动摘要。
- 不从普通对话中隐式推断长期记忆。
- 不允许长期记忆覆盖系统指令、开发者指令、安全策略或用户本轮明确要求。

## 方案反思

- 仅按重要度和更新时间检索，相关性不够精细；这是当前阶段为了复用既有 `store.ListMemories` 的保守选择。后续应补 query-aware 检索或 embedding，但不能先把复杂组件接进主链路。
- 显式记忆触发词较粗糙，可能把整句请求写入记忆；后续需要结构化提取和人工可编辑的来源说明。
- 记忆以 system message 注入简单直接，但要严守边界文案，并确保不会被写回业务历史，否则会造成上下文自我污染。
